## Exercise 3 - Individual Proposal for the Course Project

**Proposer:** Nguyen Bach Thanh Nhan (Student ID: `25127111`)  
**Project Track Selection:** Personal Productivity & Urban Mobility Assistant  
**Project Title:** **DynamicCommute: Adaptive Multi-Modal Commute Assistant with Real-Time Traffic & Dynamic Constraints Reasoning**

### 1. Problem Statement & Target Context
- **Target Audience:** Daily urban commuters (university students, office workers, delivery riders) in congested metropolitan areas such as Ho Chi Minh City.
- **Core Pain Point:** In dynamic urban environments, standard navigation tools (e.g., Google Maps) solve static shortest-path problems but fail to reason about multi-dimensional user constraints, dynamic micro-events (e.g., flash flooding, localized peak-hour congestion, narrow alleys), and natural language requests. Commuters often ask ambiguous, constraint-laden questions like: *"I need to reach campus by 8:00 AM on my motorbike, but please avoid flooded roads and narrow alleyways even if it takes 5 minutes longer."*
- **Problem Formulation:** Transform ambiguous natural-language commute requests into a constrained multi-criteria shortest path problem over a dynamic road graph, verify road feasibility, and return an explainable, robust route.

### 2. Independent Innovation & Differentiation from Group Baseline
While the baseline group project focuses on a general query assistant, this proposal introduces distinct domain complexity:
- **Dynamic Multi-Attribute Graph Formulation:** Instead of static distances, the system models real-time traffic speeds, localized flooding risk levels, and vehicle restrictions as dynamic edge weights.
- **Separation of Reasoning and Computation:** Generative AI is strictly isolated to natural language understanding and constraint extraction, whereas path calculations and constraint satisfactions are offloaded entirely to transparent, deterministic graph algorithms.

### 3. Application of Computational Thinking (The 4 Pillars)
1. **Decomposition:**
   - *Natural Language Understanding (NLU):* Parse user prompts into structured constraints (Origin, Destination, Arrival Deadline, Avoidance Rules, Vehicle Type).
   - *Traffic State Ingestion:* Retrieve and cache live traffic congestion index and weather/flooding alerts.
   - *Deterministic Path Optimization:* Recalculate optimal edge weights and solve the pathfinding problem.
   - *Response Synthesis & Explanation:* Translate the calculated route into an actionable step-by-step itinerary with transparent justifications (e.g., *"Route via Dien Bien Phu was avoided due to a 25-minute congestion delay"*).
2. **Pattern Recognition:**
   - Detect recurring historical rush-hour bottlenecks across specific time intervals (07:00–08:30 and 17:00–18:30).
   - Recognize recurring user intent templates (e.g., Fastest Route vs. Weather-Safe Route vs. Fuel-Efficient Route).
3. **Abstraction:**
   - Represent the urban transportation network as a directed, weighted multigraph $G = (V, E, W)$, where vertices $V$ represent intersections and edges $E$ represent road segments.
   - The edge weight function abstracts real-world complexity:  
     $$W_e = \frac{\text{Length}_e}{\text{Speed}_{\text{real-time}}} \times (1 + \alpha \cdot \text{CongestionLevel}) + \beta \cdot \text{FloodPenalty}$$
   - Non-essential physical details (e.g., road scenery, pedestrian crossings) are discarded to maintain algorithmic efficiency.
4. **Algorithm Design:**
   - **Deterministic Engine:** Implement **Time-Dependent Dijkstra / A\*** with dynamic weight updates to guarantee mathematically sound, reproducible shortest paths.
   - **Fallback & Routing Mechanism:** If live traffic APIs become unreachable, the system automatically falls back to static historical traffic weights and issues a warning to the user.

### 4. Alignment with Minimum System Requirements (R1 – R8)
- **R1 (Boundary & Scope):** 10 explicit use cases focusing on urban commute planning; explicit non-goals include handling real-time turn-by-turn GPS tracking.
- **R2 (Deterministic Capability):** A custom A* / Dijkstra algorithm implementation with dynamic heuristic adjustments.
- **R3 (Data / Retrieval):** Graph representation built on OpenStreetMap / GeoJSON network data with structured live traffic mock/API feeds.
- **R4 (AI-Enabled Capability):** An LLM acting strictly as an intent classifier and structured parameter extractor (outputting validated JSON schemas).
- **R5 (Routing & Orchestration):** Central pipeline directing queries: input validation $\to$ LLM parsing $\to$ parameter validation $\to$ graph search engine $\to$ natural language response synthesis.
- **R6 (Interface):** An interactive web-based chat and map interface (Streamlit or React prototype).
- **R7 (Reliability & Safeguards):** Strict parameter validation (e.g., checking if locations exist within bounded city coordinates), timeout handlers, and refusal logic for out-of-scope requests.
- **R8 (Evaluation & Improvement):** Benchmark suite of 50 test scenarios evaluating path validity, latency, constraint adherence rate, and before/after improvements through heuristic optimization.

### 2. Do you have any experience or tips for using AI?

Through practical experience in technical courses, I have established a set of core principles to ensure AI is used responsibly, ethically, and productively:

#### Tip 1: Treat AI as an Assistant, Not an Oracle (Mandatory Verification)
* **Insight:** LLMs do not "know" truth; they generate probabilistic token sequences. Consequently, they frequently hallucinate non-existent software libraries, incorrect mathematical formulas, or buggy algorithmic edge-case logic.
* **Practice:** Never accept AI-generated output as authoritative truth. Every piece of code or algorithmic logic produced with AI assistance must be accompanied by **independent validation, manual line-by-line tracing, and automated unit tests** before being integrated into our project repository.

#### Tip 2: Apply the Principle of Separation (Perception vs. Computation)
* **Insight:** As emphasized in Computational Thinking, AI is a single component, not the entire architecture. LLMs excel at linguistic parsing, text extraction, and synthesis, but they are unreliable for strict arithmetic, combinatorial optimization, and deterministic graph search.
* **Practice:** Never prompt an LLM to calculate the shortest path directly. Instead, employ the LLM solely to parse unstructured user input into a validated, structured schema (e.g., JSON), and delegate all calculations to deterministic, provable algorithms (e.g., A* or Dijkstra).

#### Tip 3: Strict Information Hygiene and Security
* **Insight:** External AI interfaces may store, log, or retrain on submitted prompt contents, presenting severe privacy and academic integrity hazards.
* **Practice:** **Never input credentials, personal identification, API secret keys, or confidential institutional data into public AI prompts.** Always abstract sensitive inputs using synthetic mock data and generalized variable names when troubleshooting logic.

#### Tip 4: Context-Rich, Constraint-Driven Prompting
* **Insight:** Broad, unconstrained queries produce generic, low-quality code that often violates specific project guidelines.
* **Practice:** Provide explicit boundaries, data types, and interface contracts. Constrain the AI by specifying what it *must not* do (e.g., *"Write a Python function to compute edge weights. Do not use external graph libraries like NetworkX; implement using raw adjacency lists and handle zero-division edge cases."*).

#### Tip 5: Intellectual Ownership and Explainability
* **Insight:** Submitting code or logic that a student cannot defend during an oral evaluation undermines academic integrity and professional competence.
* **Practice:** Abide strictly by the rule: **If you cannot explain why every single line works, you do not own the solution.** AI should enhance problem-solving velocity, but the responsibility for correctness, design trade-offs, and failure analysis rests entirely with the human engineer.
